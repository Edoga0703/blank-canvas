# Capiversa CRM 1.3.01 — correcciones y despliegue

## Alcance

Esta entrega parte del código de `capiconversa-crm-v1.3.00.zip` recibido el 29-10-2026. Conserva la interfaz y las integraciones existentes. El ZIP contiene código fuente; no incluye `node_modules`, `.output` ni credenciales de servidor. La compilación local de producción y `tsc --noEmit` se completaron antes del empaquetado. No se aplicaron migraciones a una base real ni se probaron envíos reales a D-API, Meta, Telegram o Drael.

## Correcciones principales

1. **Instalaciones históricas v1.3.00.** La migración `20261029110000_automation_legacy_preflight.sql` retira cualquier FK de `automation_conversation_control.instance_id` hacia `whatsapp_instances` antes del backfill del UUID centinela y añade columnas de lease si faltan. La migración `20261029150000_automation_v1301.sql` consolida el estado, índices y políticas. Ambos archivos tienen copia idéntica en `supabase/migrations/` y `docs/sql/`.
2. **Ejecución de flujos.** `automation_start_execution` crea o repara la ejecución, reclama conversación y encola el primer job en una sola transacción. `automation_resume_waiting` despierta la espera y encola el siguiente job en una transacción. Los eventos y jobs se cierran mediante el dueño del lease; otro worker no puede cerrar el trabajo ajeno.
3. **Mensajes entrantes.** D-API y Meta persisten primero el evento en `automation_events`. Si ningún flujo toma el mensaje, una cola durable llama al motor anterior de atención. El cron recupera cortes del proceso serverless. Se corrigió también el uso de identificadores inexistentes en el ingreso Meta y Uazapi.
4. **Meta Lead Ads.** El webhook persiste cada entrega en `meta_lead_deliveries` antes de responder 200; el worker reintenta y enlaza el card creado. Si Meta no incluye `page_id` en `change.value`, se usa `entry.id`.
5. **Meta CAPI.** `meta_capi_reserve_event` reclama la clave de deduplicación con campos obligatorios y lease. Si la reserva falla, no se envía el evento. El estado final solo lo escribe el dueño del lease.
6. **Seguridad.** Se eliminaron valores por defecto de claves Supabase service role, D-API y R2 del código y de Vite. D-API exige secreto global o por instancia. Los enlaces de medios requieren `MEDIA_SIGNING_SECRET`. La consulta del control conversacional falla de forma segura si la base de datos devuelve error.
7. **Editor y ejecución.** La publicación valida puertos existentes, ambas ramas de bifurcaciones y esperas de respuesta, y la conexión específica requerida. El envío evita cruzar el identificador de un contacto entre canales sin identidad mapeada. La auditoría de pasos guarda nombres de campos en vez de texto o valores del nodo.

## Despliegue

1. Hacer copia de seguridad de Supabase y desplegar migraciones en orden temporal. En una base que ya aplicó `120000` y `140000`, aplicar solo `150000`. En una base donde falló `120000` por la FK del centinela, aplicar `110000`, reintentar `120000`, aplicar `140000` y finalmente `150000`. En una instalación limpia, ejecutar todas las migraciones por orden. Si `150000` detecta ejecuciones duplicadas para el mismo evento y flujo, se detiene con error explícito para conciliarlas antes de repetir.
2. Configurar como secretos de servidor `SUPABASE_SERVICE_ROLE_KEY`, `DAPI_API_KEY`, los tres valores R2 (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`), `CRON_SECRET`, `MEDIA_SIGNING_SECRET` y los secretos Meta que use la instalación. No incluirlos en variables `VITE_*`. Para el webhook D-API, configurar `DAPI_WEBHOOK_SECRET` o un `webhook_token` en cada instancia.
3. Programar solicitudes POST con `x-cron-secret: <CRON_SECRET>` cada minuto a `/api/public/hooks/process-automation-jobs`, `/api/public/hooks/process-inbound-fallbacks` y `/api/public/hooks/process-meta-leads`.
4. Rotar las claves de servicio, D-API y R2 que estuvieran en el código original, porque el ZIP anterior las incluía como valores por defecto. Borrar versiones públicas del bundle construidas con ese código.
5. Probar en staging: crear y publicar flujo de mensaje entrante → envío, probar WhatsApp, Instagram, Facebook Messenger y Telegram con conexiones reales; comprobar una respuesta de IA cuando no hay flujo, una espera y su timeout, la derivación humana, Meta Lead Ads y CAPI. Confirmar que los tres cron devuelvan `ok: true` y que no crezcan filas `pending`, `failed` o `needs_review` sin explicación.

## Límites pendientes

- Los envíos de proveedores son efectos externos. Si un worker muere después de que el proveedor aceptó el mensaje y antes de confirmar el job, un reintento podría reenviarlo. Se requiere una clave de idempotencia soportada por cada proveedor o conciliación por ID externo para garantía estricta.
- La migración y las API externas no se verificaron en una base o proveedor vivo desde este entorno. La compilación y el chequeo de tipos validan el código, no la configuración del despliegue.
- El editor sigue ofreciendo los nodos implementados en esta fase. Funciones avanzadas tipo n8n, Kommo o GHL (HTTP arbitrario, multimedia, horarios, IA como nodo, etc.) son trabajo de producto posterior; no se presentan como disponibles en 1.3.01.
